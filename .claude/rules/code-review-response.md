# コードレビューへの応答方法

PR に付いたレビューコメント(Copilot / 人間レビュアー問わず)へ対応する際は、以下を守る。

## 必須: スレッドへの個別返信

- 修正内容は **PR 本体への総括コメントだけで済ませない**。指摘してきたインラインコメントの
  スレッドそれぞれに対して、GitHub の返信(reply)として個別に返答する
- 返信は `gh api -X POST repos/<owner>/<repo>/pulls/<pr>/comments -f body="..." -F in_reply_to=<comment_id>`
  で行う(`in_reply_to` を指定しない投稿は新規スレッドになり、元の指摘と紐付かないため不可)
- 返信内容には最低限、次を含める: 対応したコミットの短縮 SHA、具体的に何を変更したか
- 全体の背景や設計判断の説明が必要な場合は、個別返信とは別に PR 本体へ総括コメントを
  追加してもよい(個別返信の代替にはならない)

## 複数コメントが同一原因の場合

- rust-reviewer.md のレビュー出力ルールと同様、同一原因(例: 依存ライブラリの排除で
  まとめて解決するもの)であっても、**各スレッドへの返信は省略せず全件に行う**
- 返信本文は使い回してよいが、宛先スレッドごとに個別の返信として投稿する

## 再レビューで新しい指摘が来た場合

- push 後に Copilot 等から新しい指摘が追加されることがある。修正 → 対応コミット → 全スレッド返信、
  のサイクルを指摘が無くなるまで繰り返す
- 対応の要否が不明な指摘(スタイル的な好み等)は `[ask]` 相当として、対応するかどうかの判断を
  返信内に明記する(黙って無視しない)

## PR 説明文を追随して更新する

- PR 作成後に追加実装・レビュー対応・設計変更などで内容が積み重なった場合、
  **PR 説明文 (`gh pr edit <pr> --body ...`) は作成時のまま放置しない**。説明文が
  実際の diff・コミット内容と乖離すると、後からレビューする人が何が最終的に
  含まれているのか diff を読まないと分からなくなる
- 更新すべきタイミングの目安:
  - 当初の説明文に無かった機能・修正が新しいコミットとして追加された時
  - レビュー対応によって設計・実装方針が当初の説明と変わった時(例: 却下した案を採用した、
    別の代替案に切り替えた)
  - `jj bookmark move` でブックマークを進めて push した直後、その回の変更が
    説明文の要約に影響する場合
  - マージ直前(最終確認のタイミングで一度、実際のコミット一覧と説明文を突き合わせる)
- 毎コミットごとに更新する必要はない。「説明文を読むだけで現在の PR の全体像が
  正しく分かるか」を基準に判断する
- 更新時は `gh pr view <pr> --json body,commits` 等で現在の説明文とコミット一覧を
  突き合わせてから書き直す。「## 経緯」「## 実装内容」に加え、レビュー対応で
  積み重なった変更がある場合は「## レビュー対応」のようなセクションを追加してよい
